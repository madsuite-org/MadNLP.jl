Linear solvers

Direct linear solvers

Each linear solver employed in MadNLP implements the following interface.

MadCore.AbstractLinearSolver — Type
AbstractLinearSolver

Abstract type for linear solver targeting the resolution of the linear system $Ax=b$.

source
MadCore.introduce — Function
introduce(::AbstractLinearSolver)

Print the name of the linear solver.

source
MadCore.factorize! — Function
factorize!(::AbstractLinearSolver)

Factorize the matrix $A$ and updates the factors inside the AbstractLinearSolver instance.

source
MadCore.solve_linear_system! — Function
solve_linear_system!(::AbstractLinearSolver, x::AbstractVector)

Solve the linear system $Ax = b$.

This function assumes the linear system has been factorized previously with factorize!.

source
MadCore.is_factorized — Function
is_factorized(::AbstractLinearSolver)

Return true if the last call to factorize! succeeded. The default returns true; solvers that can detect a failed factorization overload it. MadNLPCore does not call it; MadIPM uses it to detect a failed factorization.

source
MadCore.is_inertia — Function
is_inertia(::AbstractLinearSolver)

Return true if the linear solver supports the computation of the inertia of the linear system.

source
MadCore.inertia — Function
inertia(::AbstractLinearSolver)

Return the inertia (num_pos, num_zero, num_neg) of the linear system as a tuple.

Note

The inertia is defined as a tuple $(num_pos, num_zero, num_neg)$, with

  • $num_pos$: number of positive eigenvalues
  • $num_zero$: number of zero eigenvalues
  • $num_neg$: number of negative eigenvalues
source

A new linear solver also implements create_linear_solver, default_options, input_type and is_supported, which are called with its type.

Selecting a linear solver

The sparse linear solvers are implemented in package extensions. Each is selected with a marker type, passed as the option linear_solver; the extension is loaded together with the package it wraps (MadNLP loads MUMPS, SuiteSparse, LDLFactorizations and HSL).

MadCore.create_linear_solver — Function
create_linear_solver(linear_solver::Type, A; opt = default_options(linear_solver), logger = MadNLPLogger())

Build the linear solver selected by linear_solver for the matrix A, a sparse or dense matrix as given by input_type. Every linear solver implements it, together with default_options, input_type and is_supported, which are called with the type. A package that keeps MadCore as a weak dependency can export a plain struct FooSolver end and define these methods in its extension.

A marker such as MumpsSolver is an empty subtype of AbstractSolverMarker whose package extension names the solver implementing it with solver_type; until the extension is loaded, the MethodError names the package to load.

source
MadCore.AbstractSolverMarker — Type
AbstractSolverMarker

Supertype of the markers of the linear solvers implemented in package extensions. A marker M forwards create_linear_solver, default_options, input_type and is_supported to the solver solver_type(M).

source
MadCore.solver_type — Function
solver_type(marker::Type{<:AbstractSolverMarker})

Return the linear solver type implementing marker. Defined by the extension that implements it, e.g. MadCore.solver_type(::Type{MadCore.MumpsSolver}) = MumpsState.

source
MadCore.backend_package — Function
backend_package(marker::Type)

Return the name of the package that loads the extension implementing marker.

default_sparse_solver(nlp)

Dense linear solvers

The dense KKT systems factorize their matrix with LAPACK on the host, or with the dense library of the GPU. All use the same solver type, whose workspace selects the library.

MadCore.LapackSolver — Type
LapackSolver{T, MT, Alg, M, V, W}

Dense LAPACK solver of the matrix A::MT with the factorization Alg. It copies A into the dense buffer fact::M and factorizes it in place; sol, tau and Λ are vectors of type V on the same device. The workspace ws::W holds what the library needs (pivots, work arrays, status) and selects it by dispatch: lapack_workspace builds it for the type of fact.

LapackCPUSolver is the instance on the host; the markers LapackCUDASolver, LapackROCmSolver and LapackOneMKLSolver build it on the device of their matrix.

source
MadCore.lapack_workspace — Function
lapack_workspace(fact::AbstractMatrix; kwargs...)

Return the workspace of a LapackSolver factorizing fact in place. Each backend implements it for its matrix type, with a workspace type on which it implements the setup, factorization and solve of each algorithm.

source
MadCore.LapackCPUSolver — Type
LapackCPUSolver

Dense LAPACK solver on the host: a LapackSolver whose workspace calls the LAPACK of libblastrampoline. LapackCPUSolver(A; opt, logger) copies A, which may be a host matrix (dense or sparse) or a dense GPU array, into a host matrix before each factorization.

source
MadCore.LapackCUDASolver — Type
LapackCUDASolver

Select the dense factorizations of cuSOLVER on NVIDIA GPUs. Implemented in the extension loaded by CUDACore, cuBLAS, cuSOLVER and cuSPARSE.

source
MadCore.LapackROCmSolver — Type
LapackROCmSolver

Select the dense factorizations of rocSOLVER on AMD GPUs. Implemented in the extension loaded by AMDGPU.

source
MadCore.LapackOneMKLSolver — Type
LapackOneMKLSolver

Select the dense factorizations of oneMKL on Intel GPUs. Implemented in the extension loaded by oneAPI.

Iterative refinement

MadNLP uses iterative refinement to improve the accuracy of the solution returned by the linear solver.

MadCore.solve_refine! — Function
solve_refine!(x::VT, ::AbstractIterator, b::VT, w::VT) where {VT <: AbstractKKTVector}

Solve the linear system $Ax = b$ using iterative refinement. The object AbstractIterator stores an instance of a AbstractLinearSolver for the backsolve operations.

Notes

This function assumes the matrix stored in the linear solver has been factorized previously.

source
MadCore.KrylovIterator — Type
KrylovIterator

Select GMRES iterative refinement of the KKT system, preconditioned by the factorized KKT system, with the option iterator = KrylovIterator. The extension loaded by Krylov makes KrylovIterator(kkt; opt, cnt, logger) build the iterator and defines its default_options.

Scaling and shifts of the factorized matrix

With the options kkt_scaler, primal_shift and dual_shift, a sparse KKT system hands its linear solver a scaled and shifted copy of its matrix; iterative refinement works with the unscaled, unshifted system.

MadCore.create_kkt_linear_solver — Function
create_kkt_linear_solver(linear_solver, A, n_primal; opt, logger, kkt_scaler, primal_shift, dual_shift, kkt_ordering)

Create the linear solver of a sparse KKT system for its matrix A (lower triangle, CSC), whose first n_primal rows and columns are the primal block. With a scaler or a nonzero shift, the solver factorizes

\[W A W + \begin{bmatrix} σ_p I & 0 \\ 0 & -σ_d I \end{bmatrix}\]

(σ_p = primal_shift, σ_d = dual_shift) instead of A; without, it factorizes A itself. With an ordering other than DefaultOrdering, the solver factorizes the matrix in the pivot order of kkt_ordering, handed to it with set_permutation!.

source
MadCore.ScaledShiftedSolver — Type
ScaledShiftedSolver

The linear solver create_kkt_linear_solver returns for a scaled or shifted factorization: it keeps the scaled and shifted copy of the KKT matrix, factorizes it with the selected solver, and reads the inertia from that factorization.

source
MadCore.AbstractScaler — Type
AbstractScaler

Symmetric scaling W K W of the matrix a sparse KKT system factorizes, set with the option kkt_scaler. The KKT system itself is not scaled: the factorization is, and each solve is unscaled to match, so iterative refinement works on the unscaled system.

Available scalers: NoScaler, JacobiScaler, MaxNormScaler and RuizScaler.

source
MadCore.NoScaler — Type
NoScaler()

No scaling.

source
MadCore.JacobiScaler — Type
JacobiScaler()

W = diag(|K_ii|)^{-1/2}; a zero diagonal entry gets W_ii = 1.

source
MadCore.MaxNormScaler — Type
MaxNormScaler()

One sweep of symmetric infinity-norm scaling: W_ii = (max_j |K_ij|)^{-1/2}.

source
MadCore.RuizScaler — Type
RuizScaler(sweeps = 4)

Ruiz's symmetric equilibration: sweeps sweeps of W_ii ← W_ii (max_j |W_ii K_ij W_jj|)^{-1/2}, which drive the infinity norm of every row of W K W towards one.

source

Fill-reducing orderings

The option kkt_ordering replaces the fill-reducing ordering of the sparse linear solver by one computed once on the host, from the pattern of the KKT matrix: DefaultOrdering() (the default) leaves the ordering to the linear solver, MetisOrdering() (with Metis loaded) and AMDOrdering() (with AMD loaded) hand their permutation to the solver as its pivot order, through its user-permutation interface:

using MadNLP, Metis
madnlp(nlp; kkt_ordering = MetisOrdering())

The solvers that accept a permutation are MumpsSolver (ICNTL(7) = 1), the HSL solvers (the user pivot order of MA27, MA57, MA77, MA86 and MA97), LDLSolver, UmfpackSolver (column pre-ordering), CHOLMODSolver, PardisoMKLSolver and PanuaPardisoSolver (iparm[5] = 1), AccelerateSolver (SparseOrderUser), CUDSSSolver and SDSSolver (user_perm). Each stores it in its option *_user_perm. Pivoting and matching during the factorization still apply. Any other linear solver throws an ArgumentError with an ordering other than DefaultOrdering().

MadCore.set_permutation! — Function
set_permutation!(opt, perm) -> opt

Hand the fill-reducing permutation perm of the option kkt_ordering to a linear solver through its options opt: the solver factorizes its matrix A in the pivot order perm (row and column i of the factorized P A Pᵀ are row and column perm[i] of A) instead of computing an ordering of its own. Each solver with a user-permutation interface defines a method for its options type, which sets its option *_user_perm; opt is a copy of the options the KKT system received.

The fallback throws an ArgumentError: an ordering other than DefaultOrdering needs a linear solver that accepts a user permutation.

source
MadCore.AbstractOrdering — Type
AbstractOrdering

Symmetric fill-reducing permutation P A Pᵀ of the matrix a sparse KKT system factorizes, set with the option kkt_ordering. The permutation is computed once on the host, from the pattern of the KKT matrix, and replaces the ordering of the linear solver, which receives it through its user-permutation interface (see set_permutation!) and factorizes the KKT matrix in that order. A linear solver without such an interface supports only DefaultOrdering.

Available orderings: DefaultOrdering (the linear solver orders the matrix itself), MetisOrdering (with Metis loaded) and AMDOrdering (with AMD loaded).

source
MadCore.DefaultOrdering — Type
DefaultOrdering()

No ordering at the KKT level: the linear solver factorizes the KKT matrix as assembled, with its own fill-reducing ordering.

source
MadCore.MetisOrdering — Type
MetisOrdering()

Nested dissection of METIS. Implemented in the extension loaded by Metis.

source
MadCore.AMDOrdering — Type
AMDOrdering()

Approximate minimum degree ordering of AMD. Implemented in the extension loaded by AMD.

source
MadCore.ordering_permutation — Function
ordering_permutation(ordering::AbstractOrdering, A::SparseMatrixCSC) -> Vector{Int}

Return the permutation perm of the symmetric matrix whose lower triangle is A: row and column i of the permuted matrix are row and column perm[i] of the original, so perm[i] is the i-th pivot. Only the pattern of A is read. The methods of MetisOrdering and AMDOrdering are defined in the extensions loaded by Metis and AMD.
